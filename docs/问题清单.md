## Q01 /state 拼接长度算错 → 栈越界写

**位置**：`main/app_http.c:36-46`（`char body[1024]`）+ `main/ai_sessions.c:258-281`（`ai_sessions_dump_json`）

> **状态：部分缓解，机制仍在。** 缓冲已经从 512 提到 **1024**（正是下节"修复"的第一条建议，
> 注释写的是"512会截断成非法JSON"）—— 但那是按**症状（JSON 非法）**修的，
> **根因（累加被截断的 `snprintf` 返回值 → 负长度当 `size_t`）一行没动**，
> 而且 #038 把 `project[16]` 扩到 `[32]`、条目又长了 ~16 字节，把刚买到的余量吃掉一半。
> 下面是按**当前 1024 几何**重算（第三轮复核）的结果。

**机制**：`snprintf` 被截断时返回的是「**本该写入**的长度」，不是实际写入长度。代码直接把它累加进 `off`：

```c
for (int i = 0; i < MAX_SESSIONS && off < buflen - 48; i++) {
    off += snprintf(buf + off, buflen - off, "{...}");  // 截断时返回"本应长度" → off 可以冲过 buflen
}
off += snprintf(buf + off, buflen - off, "]");          // buflen-off 为负 → size_t 巨值 → 越界写
```

最后一行哪怕只写 `]` 和 `\0` 两个字节，落点也在 `body[1024]` 之外 —— httpd 任务栈上。

**当前触发窗口（1024 字节，离线模拟逐长度扫描）**：
`/state` 前缀 `{"lamp":"...","sessions":N,"table":` 仍占 45 字节，所以 `dump_json` 拿到的
`buflen` 是 **979**。条目长度 = `79 + proj + tool + state + tok位数 + idle位数`。

| 会话数 | 是否可达 | 说明 |
|---|---|---|
| 1~7 | ✗ | 需要的单条长度 ≥140，超出条目的物理上限 |
| **8（表满）** | ✓ **L ≥ 122** | 门槛落进现实区间，见下表 |

| 8 个会话的场景 | 条目 L | dump 后 `off` | 结果 |
|---|---|---|---|
| proj=`AI_Status`(9)、tok 5 位、idle 3 位 | 101 | 817 | 安全 |
| proj=`esp32-ai-light`(14)、tok 6 位、idle 3 位 | 109 | 881 | 安全 |
| proj 26 字节、tok 7 位（约 100 万）、idle 3 位 | 122 | 984 | **写 `]` 落点 `body+1029`，越过 4 字节** |
| proj 31 字节、tok 7 位、idle 3 位 | 127 | 1024 | **越过 44 字节** |

**第二处越界点**（易被漏掉）：`state_get` 里
`n += ai_sessions_dump_json(...)` 拿到的 `n` 已经 >1024，
紧接着 `snprintf(body + n, sizeof(body) - n, "}")` 又是一次**负长度 → `size_t` 巨值**的写。

即：需要 **8 个会话同时在线**（表满，串口会打"会话表满，驱逐最旧会话"）**且**项目名 ≥26 字节
**且** token 七位数。比 512 时代（5 个普通会话就踩线）难得多 —— 但长会话满编是这个项目的
**正常状态**，不是极端输入。

**症状**：
1. 越界写 → 撞栈 canary / 破坏 httpd 局部变量 → panic 重启或随机异常；
2. 窄窗口副作用：剩余空间恰好不够写 `]` 时 → `/state` 返回**非法 JSON** →
   看门狗 `json.loads` 抛异常、静默跳过巡检 → 死卡永远不被清理
   （`hook/esp_light_watchdog.py` 的 `board_state`/`proc_rules`）。

**验证方法**：
```bash
# 造 8 个会话：项目名 31 字节 + token 7 位（cwd basename 会被截到 31）
for i in 1 2 3 4 5 6 7 8; do
  curl -s -X POST "http://192.168.1.20/events?event_type=prompt-submit&src=claude&tok=1234567" \
       -d "{\"session_id\":\"t$i\",\"cwd\":\"/home/u/this-is-a-very-long-project\"}" >/dev/null
done
curl -s http://192.168.1.20/state   # 观察：第 8 条是否被截断 / JSON 是否合法 / 串口是否 Guru Meditation
```
（更快的等价做法：临时把 `body[1024]` 改小到 192，窗口立刻放到 2 个会话就能撞；
⚠️ 改小后**别烧进日常用的固件**。）

**证据**：离线模拟复刻 `snprintf` 的"返回本应长度"语义 + 当前 1024 几何（见文末附录脚本）。

**修复**：
```c
int ai_sessions_dump_json(char *buf, int buflen)
{
    int off = 0;
    int left = buflen - off;
    if (left <= 0) return 0;
    off += snprintf(buf + off, left, "[");
    for (int i = 0; i < MAX_SESSIONS; i++) {
        left = buflen - off;
        if (left < 64) break;                       // 留出尾部余量
        ...
        int w = snprintf(buf + off, left, "{...}");
        off += (w >= left) ? (left - 1) : w;        // ★ 关键：截断时按实际写入长度收敛
        if (w >= left) break;                       // 已经写满，别再拼
    }
    left = buflen - off;
    if (left > 0) snprintf(buf + off, left, "]");
    return off;
}
```
配套：`state_get` 的收尾 `snprintf` 也要先 clamp `n`（`if (n > (int)sizeof(body) - 2) n = sizeof(body) - 2;`）。
`body[1024]` 已经够用，**别再靠加缓冲来压这个问题**——条目长度是随字段扩容增长的（#038 就是例子），
而 1024 是 httpd 任务栈能承受的上限附近（默认 `stack_size = 4096`，这个数组已占 1/4）。
**根因是"负长度当 size_t"这一类写法，值得在项目里全局搜一遍**
（`grep -n "buflen - \|sizeof(.*) - n" main/`）。

**工作量**：~30 分钟（含回归验证）。

## Q02 局部刷新的过渡缓冲与 DMA 抢跑 → 卡片间歇撕裂

**位置**：`main/app_display.c:62`（`s_flush_buf`）、`:107-121`（`flush_region`）
配合 `components/bsp/ST7789.c:121-122`（`trans_queue_depth = 4`、`on_color_trans_done = NULL`）

**机制**：`esp_lcd_panel_io_tx_color` **不等待传输完成**，只把事务排队就返回。
官方头文件 `esp_lcd/include/esp_lcd_panel_io.h:60-63` 明说：

> This function will package the command and RGB data into a transaction, and push into a queue.
> The real transmission is performed in the background (DMA+interrupt).
> The caller should take care of the lifecycle of the `color` buffer.
> Recycling of color buffer should be done in the callback `on_color_trans_done()`.

调用链：`Vernon_ST7789T.c:221` → `esp_lcd_panel_io_tx_color` → `esp_lcd/spi/esp_lcd_panel_io_spi.c:405`
`spi_device_queue_trans` 后立即返回，函数末尾也没有等待（`:414`）。
驱动里唯一的等待在下一次 `tx_color` 的**开头**（`:331-337` 回收在途事务）——
而 `flush_region` 的 `memcpy` 在 `draw_bitmap` **之前**，所以那次等待救不了它：

```
draw_card(0) → memcpy(A) → draw_bitmap 排队 A，返回；A 正在被 DMA 读（约 3ms）
draw_card(1) → memcpy(B) ← 覆盖正在传输的缓冲；之后 draw_bitmap 才等 A 完成
```

单卡 101×148×2 ≈ 29.9KB @80MHz ≈ 3ms；而 `draw_card` 画一张卡（约 1.5 万次 `px()` 写 + 文字）
也要 ~2-3ms —— **两者同量级，所以是临界竞态**：多数帧侥幸不撞，撞上就是"某张卡的右半部分显示成邻卡内容"。
一帧内连续 flush 三张卡 + 头部，第 3 张与头部 flush 也会相撞。

**验证方法**（受控实验，一次只改一个变量）：
1. 在 `flush_region` 的 `memcpy` 前临时插 `vTaskDelay(pdMS_TO_TICKS(5))` → 撕裂**必然**出现（放大了竞态）；
2. 按下面的修复加回调+信号量等待 → 同样的延时下撕裂消失；
3. 撤掉延时 → 观察是否仍有偶发（这才是真实概率）。

**修复**（顺序很重要：`trans_queue_depth=1` 单独改**无效**，因为 memcpy 仍早于调用）：

```c
/* ST7789.c：注册传输完成回调（回调在 ISR 上下文，必须 FromISR） */
static SemaphoreHandle_t s_lcd_idle;
static bool IRAM_ATTR on_color_done(esp_lcd_panel_io_handle_t io,
                                    esp_lcd_panel_io_event_data_t *e, void *ctx)
{
    BaseType_t woken = pdFALSE;
    xSemaphoreGiveFromISR(s_lcd_idle, &woken);
    return woken == pdTRUE;
}
/* 创建 io 前：s_lcd_idle = xSemaphoreCreateBinary(); xSemaphoreGive(s_lcd_idle);
   esp_lcd_panel_io_register_event_callbacks(io_handle, &cbs, NULL);  */

/* app_display.c flush_region：memcpy *之前* 等上一次传输完成 */
if (s_lcd_idle) xSemaphoreTake(s_lcd_idle, portMAX_DELAY);
memcpy(...); esp_lcd_panel_draw_bitmap(...);
```
注意信号量初值要给 1（开机第一次 flush 不该阻塞），并在 `flush_all()` 走同一套等待。

**工作量**：~1 小时（改 BSP + 显示层 + 肉眼看帧）。

## Q03 Stop 事件（终态）投递最脆

**位置**：`hook/claude_token_hook.py:84-91`，对照 `hook/ai_status_hook.cmd:10`（由 `install_hooks.py:56-75` 生成）

**机制**：其它 6 个事件走 cmd 包装 + `curl -m 3 --retry 3 --retry-all-errors`；
唯独 Stop 走了带 token 提取的 Python 脚本：

```python
opener.open(req, timeout=2).read()      # 单次尝试、2s 超时，无重试
```

而 #010 实测过：弱射频下 **TCP 握手本身就可能卡 3 秒**。也就是说 **决定灯回到绿的那个事件，
是唯一没有重试、且超时最紧的通道**；Python 冷启动 ~300ms 还要再吃掉一部分预算。
#013「卡黄」的根因正是 stop 丢失（目前靠闲置提醒/看门狗兜底，属于自愈而非修复）。

**验证方法**：把路由器 2.4G 调弱或临时把 `timeout` 降到 0.5s，连发多轮 Stop → 统计
`~/.ai_status/tok_hook.log` 里 `post failed` 的比例。

**修复**（保留 token 提取，只补投递语义）：
```python
for attempt in range(3):
    try:
        opener.open(req, timeout=3).read(); ok = True; break
    except Exception:
        time.sleep(0.3)
```
更稳：失败时把原始 payload 转交 `cmd /c ai_status_hook.cmd stop claude` 重发一次
（状态设置是幂等的，重复无害 —— 与 #010 的结论一致）。顺带给 `tok_hook.log` 加个大小上限/轮转。

**工作量**：~20 分钟。

## Q04 每个事件都整表写 NVS

**位置**：`main/ai_sessions.c:187`（无条件 `s_dirty = true;`），调用点 `main/app_display.c:485`

**机制**：上面刚按"状态真的变了"置脏（`:168-171`），函数末尾又无条件置了一次，节流意图被完全抵消。
于是 Claude 的 pre/post-tool-use 事件流 = **每事件一次 NVS blob 写 + commit**。
一次写 842 字节 ≈ 29 个 entry，约每 4 次写满一页触发一次擦除；除了 flash 寿命，
`nvs_commit` 期间还会阻塞显示任务（擦除可达数十 ms）→ 掉帧。

**验证方法**：在 `ai_sessions_maybe_save` 里加个计数器，`ESP_LOGI` 每 100 次打印一次；
跑一轮真实会话，与 `hook_exec.log` 的事件条数对比（预期两者同量级 = 问题确认）。

**修复**：删掉 `:187` 那行；并在 `maybe_save` 里加时间节流：
```c
static int64_t s_last_save_ms;
if (!s_dirty || now_ms() - s_last_save_ms < 30000) return;   // 30s 一次足够
s_last_save_ms = now_ms();
```
（注意：停电会丢最近 30s 的会话表 —— 相对 #023 要解决的"活会话被误杀"，这个取舍是可接受的。）

**工作量**：~15 分钟。

## Q05 字体表越界读

**位置**：`main/app_display.c:130-141`（`draw_char`），`main/font5x7.h:12`（`k_font5x7[128][7]`）

**机制**：`k_font5x7[(int)(unsigned char)c]` —— 索引范围 0~255，表只有 128 项，
c ≥ 128 时读到表外最多 889 字节（`.rodata`，读到的是别的常量，表现为乱画的字形，不会崩）。

**触发条件**：`draw_text` 的入参含非 ASCII 字节。目前 `project` 在 HTTP 侧已过滤
（`app_http.c:193-197` 只留 0x20~0x7E），但 `last_tool`（`app_http.c:177-183` 扫 `tool_name`）
**没有过滤** —— 一旦某个工具的 tool_name 带非 ASCII（或扫描把其它字段误当 tool_name），就会命中。

**修复**：`draw_char` 入口加一句钳位，一行解决：
```c
if (c < 0x20 || c > 0x7e) c = '?';    /* 表只覆盖 ASCII */
```
（顺带：`draw_text` 里的 `toupper` 同理，钳位放 `draw_char` 里最省事。）

**工作量**：5 分钟。

## Q06 NVS blob 缺边界校验

**位置**：`main/ai_sessions.c:386-430`（`ai_sessions_load`），`main/ai_state.c:37-45`

**机制**：`load` 只校验 `len < 10` 和版本号，然后 `uint8_t n = buf[9];` 直接用于循环，
既没校验 `n <= MAX_SESSIONS`，也没校验 `len >= 10 + n * sizeof(slot_blob_t)`。
blob 被写坏（掉电中断、NVS 局部损坏）时按 `n=255` 读 → **越过 842 字节的栈缓冲一路读下去**。
另外 `b.state` 取出未钳位，而 `ai_state_name(s)` 对负值会负索引（`k_state_names[-1]`），
`ai_event_name(e)` 同理。

**修复**：
```c
if (len < 10 || buf[0] != 3) { ...废弃... }
uint8_t n = buf[9];
if (n > MAX_SESSIONS) n = MAX_SESSIONS;
if (len < 10 + (size_t)n * sizeof(slot_blob_t)) { ...废弃... }
...
s->state = (b.state <= AI_STATE_ERROR) ? (ai_state_t)b.state : AI_STATE_IDLE;
```
并在 `ai_state_name`/`ai_event_name` 里改成 `(s >= 0 && s <= X)`（负值也返回 `"?"`）。

**工作量**：~20 分钟。**与 Q10 的 `ts` 粘滞同属"让坏输入不产生坏后果"这条线，建议一起做。**

## Q07 读 body 超时未重试，残留字节污染连接

**位置**：`main/app_http.c:134-149`

**机制**：`httpd_req_recv` 返回负值（`HTTPD_SOCK_ERR_TIMEOUT` 等）时直接 `break`，
`content_len` 剩下的字节仍留在 socket 里。当前 curl 每次新建连接所以不显形；
一旦改成 keep-alive（或换成 Python `urllib` 复用连接、看门狗那种带 `Connection: keep-alive` 的客户端），
下一个请求的解析就会从残包中间开始 → 事件错乱/丢失。

**修复**：区分错误类型，超时就重试而不是放弃：
```c
int r = httpd_req_recv(req, buf, want);
if (r == HTTPD_SOCK_ERR_TIMEOUT) continue;   /* 超时重试 */
if (r <= 0) break;                            /* 真错误/断开才放弃 */
```
（并给循环加个最大重试次数，避免死循环。）

**工作量**：~15 分钟。

## Q08 会话表跨任务无同步 + 卡片迟到 15s

**位置**：`main/main.c:44`（`app_display_init()`）与 `:48`（`ai_sessions_load()`）之间夹着 `:47` 的 `app_wifi_start(15000)`

**机制**：显示任务在 `:44` 就起来了，之后每 50ms 调 `ai_sessions_tick()` / `ai_sessions_aggregate()`；
而 `ai_sessions_load()` 在 main 任务里**最多 15 秒后**才往同一张表里写 —— 两个任务无锁并发访问同一份全局数组。
后果①：load 写到一半被 tick/aggregate 读到（半成品状态，单帧显示错误）；
后果②：重启后卡片要等 WiFi 等待结束才出现。

**修复**：把 `ai_sessions_load()` 移到 `app_display_init()` **之前**（会话表是纯内存状态，
不需要等网络；`main.c:41` 的 `ai_sessions_init()` 之后紧接着 load 即可）。
这样"表的所有者在显示任务启动前就填好了"，比加互斥锁更简单也更彻底。

**工作量**：~10 分钟（移动一行 + 验证重启恢复 #023 仍然生效）。

## Q12 ERROR→DONE 降级空转（#018 的设计未生效）

**位置**：`main/ai_sessions.c:197-221`（`ai_sessions_tick`）

**机制**：三个分支用**同一个 `age`**（= `now - last_event_ms`）做判据，而降级时没有推进这个基准：

```c
int64_t age = now - s_slots[i].last_event_ms;
if (state == WORKING && age >= 5min)        { used = false; }          // ①
else if (state == ERROR && age >= 10min)    { state = DONE; ... }      // ② 降级
else if (state != WORKING && age >= 10min)  { used = false; }          // ③ 幽灵清理
```

ERROR 会话到 10 分钟时走 ② 变成 DONE，但 `last_event_ms` 没动 —— **下一个 tick（50ms 后）**
就走 ③ 把它清理掉。所以 #018 承诺的「ERROR 晾 10 分钟 → 降级 DONE（绿常亮）」**从来没有出现过**，
卡片是直接消失的。

**影响**：
1. 实现与自己的问题记录不符（#018 的结论是"红闪封顶 10 分钟后降级完成"）；
2. 用户看到的是"卡片凭空消失"而不是"变绿"，排查时无法区分"审批超时降级"和"进程被杀清理"；
3. 聚合灯从红直接变暗，少了一次"这轮有结果"的绿提示。

**验证方法**（用 `ts` 加速，10 分钟 → 10 秒）：
```bash
curl -s -X POST "http://192.168.1.20/events?event_type=permission-request&ts=60&src=claude" \
     -d '{"session_id":"q12","cwd":"/a/q12test"}'
sleep 9;  curl -s http://192.168.1.20/state     # 预期（#018 设计）：ERROR 红闪
sleep 2;  curl -s http://192.168.1.20/state     # 实际：卡片已消失；设计意图：DONE 绿常亮
```

**修复**：降级时同步推进计时基准，让 DONE 卡按自己的 10 分钟幽灵超时再走：
```c
s_slots[i].state = AI_STATE_DONE;
s_slots[i].state_since_ms = now;
s_slots[i].last_event_ms  = now;   /* ★ 不推进的话下一 tick 就被 ③ 清掉 */
```

**工作量**：10 分钟。

## Q13 安装器标记表漏了 token 脚本 → Stop hook 越装越多

## Q14 Notification 的 permission 判定被 `permission_mode` 击穿（闲置提醒全变红）

**位置**：`main/app_http.c:225-234`

**机制**：Claude Code 的 hook 输入有一个**公共基础 schema**，从 `claude.exe` 里提取出来是：

```js
v = f(() => d({ session_id, transcript_path, cwd,
                prompt_id: 可选, permission_mode: 可选, agent_id: 可选,
                agent_type: 可选, effort }))

// Notification 事件 = 基础 schema .and() 事件专有字段：
Xq = f(() => v().and(d({ hook_event_name: "Notification",
                         message, title: 可选, notification_type })))
```

也就是说 **Notification 的 body 里带着 `"permission_mode":"default"`**。而固件判断"要不要红灯"用的是
`strstr(body, "permission")` —— 这个词在 `permission_mode` 里必然出现，
于是**每一个 Notification 都被判成权限请求 → 红**（`permission_mode` 在本机路径下落在 body 约 290 字节处，
在 512 字节窗口内）。

**影响**：
1. 闲置提醒（60 秒无互动）本该绿，现在红 —— 正是 #013 想消除的"语义噪音"；
2. #013 的第二个设计「闲置提醒顺便当丢失 Stop 的自愈信号」**完全失效**（卡黄的灯不会自己回绿）；
3. 配合"晾 2 分钟升级红闪"，一个只是闲置的会话会闪起 `OVERDUE!`，看起来像出事。

**修复（推荐，改动最小）**：改用 `notification_type` 判定 —— Claude Code 的取值只有 4 个，
用现成的 `json_scan_string` 扫这个字段（同样对截断免疫）：

| notification_type | 含义 | 灯 |
|---|---|---|
| `permission_prompt` | 要权限 | ERROR（红闪) |
| `elicitation_dialog` | 弹了要人回答的框 | ERROR |
| `idle_prompt` | 闲置提醒 | DONE（绿） |
| `auth_success` | 认证成功 | DONE |

兜底链：`notification_type` → 扫 `message` → 最后才退回现在的 body 全文（兼容老版本 payload）。

**修复（更彻底，顺手把阶段 3 的欠债还掉）**：新版 Claude Code **原生支持 `PermissionRequest` 输入事件**
（schema：`{hook_event_name:"PermissionRequest", tool_name, tool_input, permission_suggestions?}`），
把它加进 `CLAUDE_EVENTS`（`install_hooks.py:35-43`）即可 —— 固件里
`AI_EV_PERMISSION_REQUEST → ERROR` 的映射（`ai_state.c:84-86`）**本来就有**，
Notification 的嗅探逻辑可以整段退役（ZCode 走的就是这条原生通道）。

**上机确认（30 秒）**：让一个 Claude 会话闲置 60 秒触发闲置提醒，然后 `curl /state` ——
若该卡是 `ERROR`（两分钟后变 `RED_FLASH`）本条确认；修好后应为 `DONE`。

**证据**：从 `claude.exe` 提取的 hook schema（基础 `v()` 字段 + `.and()` 扩展）与 `notification_type` 的四个取值。

**工作量**：20 分钟（推荐版）/ 40 分钟（原生 PermissionRequest 版，含 hook 重装）。

## 附录：Q01 的离线验证脚本

第二轮的窗口数字不是手算的，是用下面这个脚本逐长度扫描出来的（复刻 `snprintf` 的
"返回本应长度"语义 + `/state` 的 45 字节前缀）：

```python
def snprintf_state(cap, payload):
    return len(payload), (cap > 0)      # cap<=0 -> 负长度转 size_t -> 越界写

def dump(entries, buflen):
    off = 0; off += len("[")
    for e in entries:
        if not (off < buflen - 48): break
        if off > 1: off += 1
        _, ok = snprintf_state(buflen - off, e)
        if not ok: return off, True
        off += len(e)
    _, ok = snprintf_state(buflen - off, "]")
    return off, not ok

HDR = len('{"lamp":"YELLOW_BREATH","sessions":8,"table":')
for n in range(1, 9):
    bad = [L for L in range(70, 130) if dump(["x"*L]*n, 512 - HDR)[1]]
    if bad: print(n, bad)
```

修好 Q01 之后建议把这个脚本改成一份**单元测试**（`docs/` 里留档或做成 host 端测试），
输入真实形状的条目跑一遍 —— 这类"拼接长度"的 bug 只靠肉眼看是抓不住的。
