# AI 状态提示灯 · 学习路线

> 项目目标：用 Waveshare ESP32-C3-LCD-1.47 做一个桌面 AI 状态红绿灯。
> 黄灯 = AI 工作中，红灯 = 报错/需要权限确认，绿灯 = 已出结果。
> LCD 屏幕按项目/会话分区显示状态，通过 WiFi 无线接收事件。
>
> 学习主线：**ESP-IDF 工程体系 → FreeRTOS → WiFi/HTTP → LVGL UI**，每阶段先跑通最小例程再迭代。

## 整体架构

```
┌─────────────┐  hook    ┌──────────────────┐  HTTP POST /events   ┌─────────────────────┐
│ Claude Code  │────────→│ 本机 hook 脚本     │────────WiFi────────→│ ESP32-C3 固件        │
│ (会话事件)    │         │ (读stdin→发JSON)  │   (局域网)           │ HTTP服务器→状态机→UI  │
└─────────────┘         └──────────────────┘                      └─────────────────────┘
```

事件格式（沿用 ai-light 项目的 HookEvent 协议）：

```json
{
  "event_type": "session-start | prompt-submit | pre-tool-use | permission-request | notification | stop | session-end",
  "session_id": "…",
  "cwd": "D:\\path\\to\\project",
  "tool_call": "Bash",
  "tool_source": "claude-code"
}
```

状态映射（与 ai-light 设计一致）：

| Hook 事件 | 灯状态 |
|---|---|
| session-start | 出现灯组，空闲(暗) |
| prompt-submit / pre-tool-use / post-tool-use | **黄灯**（脉动） |
| notification / permission-request | **红灯** |
| stop | **绿灯** |
| session-end | 灯组消失 |

多会话聚合规则：`error > working > done > idle`（最严重优先）。

### 配网方案选型（先定后写代码）

| 方案 | 原理 | 优点 | 缺点 | 用在哪 |
|---|---|---|---|---|
| menuconfig 硬编码 | 编译时写入 SSID/密码 | 最简单，专注学 WiFi+HTTP 主线 | 换网要重编译 | **阶段 2 第一步（先用它）** |
| SoftAP 网页配网 | 设备先变身热点，手机连上后访问 192.168.4.1 输入家里 WiFi | 不装 APP、像真产品 | 要写配置页+存 NVS | **阶段 2 第二步（升级）** |
| SmartConfig | 手机 APP 广播凭据 | 无需额外交互 | 要装 APP、限 2.4G、成功率一般 | 不选 |
| BLE Provisioning | 官方 wifi_prov_mgr + 手机 APP | 安全、官方推荐 | 流程最复杂、代码量大 | 暂不选 |

路线：**先用 menuconfig 硬编码把 WiFi+HTTP 主线跑通，再升级 SoftAP 网页配网**——符合"先跑通最小例程再优化"的原则。

学习点：
- [ ] `esp_wifi` STA 模式连接、自动重连、事件循环（esp_event）
- [ ] `esp_http_server`：注册 POST /events URI handler
- [ ] JSON 解析（cJSON）
- [ ] FreeRTOS 入门：任务创建、队列（HTTP 任务收事件 → 队列 → 显示任务消费）
- [ ] NVS 存储 WiFi 凭据（配网升级时引入）

## 阶段 5：扩展 ZCode 支持 ✅ 2026-09-26 端到端打通

**最终方案**（六轮攻坚，详见问题记录 #014/#015）：本地插件 ai-status-hooks（command 型 hook）→ cmd 包装 v3 → 固件 /events。灯随 ZCode 工具调用实时变化。

**已验证"翻译层很薄"的判断**：固件零改动，只新写了配置安装逻辑。

**Hook 机制的知识框架（2026-09-25 补记）**：
- 模式通用：所有 hook 系统本质都是"生命周期事件 → spawn 命令 → stdin 喂 JSON → 退出码语义"
- 配置不通用：每家 AI 工具的配置文件、事件名、字段、退出码约定各自为政，需按文档适配
- 我们的架构：ESP32 是"通用事件接收器"（/events 认 kebab-case + PascalCase 两套事件名），
  接新工具 = 写薄翻译层（改配置转发事件），固件零改动

**实际适配差异**：

| | Claude Code | ZCode |
|---|---|---|
| 配置文件 | `~/.claude/settings.json` | `~/.zcode/cli/config.json` |
| 结构 | `hooks.<Event>` | `hooks.events.<Event>` + **必须 `enabled: true`**（默认关闭） |
| 权限事件 | 用 `Notification` 承载 | **原生 `PermissionRequest`**（映射更准） |
| hook 类型 | command 型 | process 型（参数数组直跑，官方推荐） |
| 有无 SessionEnd/Notification | 有 | 无 |
| stdout | 宽松 | **严格 JSON 校验**（空输出安全，乱输出会报错） |
| 执行方式 | 同步 | 同步（每次工具调用内联付出 hook 延迟） |

**双档重试策略**（因为 hooks 同步执行，延迟由 AI 工具买单）：
- fast 档（pre/post-tool-use、prompt-submit）：2 秒+1 重试——丢了下次工具调用马上补
- slow 档（permission/stop/session）：3 秒+3 重试——丢了灯就卡死（#009 教训）
