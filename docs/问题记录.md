## #001 Git Bash / ZCode 环境下无法使用 ESP-IDF

**日期**: 2026-09-25
**阶段**: 环境搭建

**现象**：
执行 `C:\esp\v6.1\esp-idf\export.bat` 报错：
```
This .bat file is for Windows CMD.EXE shell only.
```

**原因**：
乐鑫的 `export.bat` 开头检查了 `MSYSTEM` 环境变量——只要它被定义就认为你在 MSYS/Git Bash 里，直接退出。而 ZCode 的终端是 Git Bash，天然带着 `MSYSTEM=MINGW64`，并且会把它传给子进程（即使 `env -u MSYSTEM` 清了，bash profile 又会补回来）。

**解决**：
写一个包装脚本 `idf.bat`（项目根目录），先 `set "MSYSTEM="` 再 `call export.bat`，以后所有 idf.py 命令都通过它执行：
```
cmd //c "D:\Xxx\Project\Esp32\AI_Light\idf.bat build"
```

**学到什么**：
- ESP-IDF 的环境加载脚本会区分 shell 类型（`export.bat`/`export.sh`/`export.fish` 各一份）
- Windows 下环境变量"定义了但为空"和"未定义"是两回事，`set "MSYSTEM="` 才是彻底清除的正确写法
- 交叉工具链（xtensa-esp-elf-gcc 等）不在系统 PATH 里，每次新开 shell 都要重新加载 IDF 环境——这是嵌入式开发的日常

## #002 ESP-IDF 工具链下载超时（GitHub 无法直连）

**日期**: 2026-09-25
**阶段**: 环境搭建

**现象**：
`install.bat` 在下载 `xtensa-esp-elf-gdb` 时反复失败：
```
WARNING: Download failure: <urlopen error [WinError 10060] 连接方在一段时间后没有正确答复...>
ERROR: Failed to download, and retry count has expired
```

**原因**：
ESP-IDF 的工具链二进制托管在 GitHub Releases 上，国内网络直连 github.com 经常超时。且安装脚本用 Python urllib 下载，不走 git 的代理配置。

**解决**：
乐鑫官方提供了 GitHub 资产镜像，安装前设置：
```bat
set "IDF_GITHUB_ASSETS=dl.espressif.com/github_assets"
set "PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple"
call install.bat
```

**学到什么**：
- ESP-IDF 安装分两部分：①Python venv + pip 包 ②交叉编译工具链下载，两部分都可能卡网络
- `IDF_GITHUB_ASSETS` 是官方钦定的镜像方案（文档: https://docs.espressif.com/projects/esp-idf/zh_CN/latest/esp32/api-guides/tools/idf-tools.html）
- 工具统一装在 `~/.espressif/`，IDF 本体在 `C:\esp\v6.1\esp-idf`，两者分离——所以重装 IDF 不用重下工具链

## #003 厂商例程 sdkconfig 里有其它芯片的遗留配置

**日期**: 2026-09-25
**阶段**: 阶段 1 建工程

**现象**：
微雪例程的 `sdkconfig.defaults` 里有 `CONFIG_SPIRAM=y`、`CONFIG_SPIRAM_MODE_OCT=y`，且顶层 `CMakeLists.txt` 的工程名居然叫 `ESP32-S3-LCD-1.47`。

**原因**：
厂商例程是从 ESP32-S3 的板子复制改的，PSRAM 配置是 S3 专用的遗留物。ESP32-C3 **没有 PSRAM**，也不支持 Octal SPIRAM；CMake 工程名纯粹没改。

**解决**：
自己工程只保留真正需要的配置（flash 4MB、自定义分区表）。教训：**参考厂商代码时逐项确认，不要整包照抄**。

**学到什么**：
- `sdkconfig.defaults` 是"种子配置"，`set-target` 后生成完整 `sdkconfig`；与目标芯片不兼容的项会被忽略并告警
- ESP32-C3 = RISC-V 单核 + 400KB SRAM + 无 PSRAM；写 UI 帧缓冲（180×320×2=115KB）时必须心里有数

## #004 Windows 批处理(.bat)的两大编码陷阱：中文注释 + printf 转义

**日期**: 2026-09-25
**阶段**: 环境搭建 / 阶段 1

**现象**：
1. `build.bat` 里的中文注释执行时报 `'剁洰褰曪紝...' 不是内部或外部命令`，且下一行 `set "MSYSTEM="` 没被执行；
2. 用 Git Bash `printf` 写入的 `call C:\esp\...` 路径变成了 `call C:ESCsp6.1...`，直接报"文件名、目录名或卷标语法不正确"。

**原因**：
1. cmd.exe 按 **GBK(代码页 936)** 解析 .bat，UTF-8 中文注释变乱码，某些字节流还会"吞掉"行尾换行，把注释和下一条命令粘成一行；
2. Git Bash 的 `printf` 第一个参数是**格式串**，`\e`、`\v`、`\a` 都会被解释成转义字符（ESC、垂直制表符、响铃），Windows 路径里的 `\esp`、`\v6.1`、`\ai-light` 全部中招。

**解决**：
- .bat 文件只用 ASCII 字符，中文说明放 .md 文档
- 写 .bat 用编辑器/Write 工具直接写，不要经过 shell 的 printf/echo 转义链

**学到什么**：
- Windows 控制台默认代码页是 GBK（`chcp` 可查），跨编码文件是批处理脚本的经典雷区
- `printf` 的格式串会吃反斜杠转义，含 Windows 路径的内容绝不能放进第一个参数
- 排查技巧：乱码信息里出现"相邻两行内容粘连"就是换行被吃了；路径里出现 `^[`（ESC）就是转义被错误解释了

## #005 IDF 6.x 编译报错：组件依赖必须显式声明

**日期**: 2026-09-25
**阶段**: 阶段 1 首次编译

**现象**：
复制厂商 BSP 后编译失败：
```
Compilation failed because ST7789.h (in "bsp" component) includes esp_timer.h,
provided by esp_timer component(s).
However, esp_timer component(s) is not in the requirements list of "bsp".
```

**原因**：
`ST7789.h` 里 `#include "esp_timer.h"`，但 bsp 组件的 `idf_component_register(REQUIRES ...)` 没列 `esp_timer`。旧版 IDF（~4.x/5.0）有一批"公共组件"会被隐式链接，厂商代码因此能编过；新版 IDF 收紧了规则，**用了谁的组件就必须声明谁**。

**解决**：
`components/bsp/CMakeLists.txt` 的 REQUIRES 加上 `esp_timer`。

**学到什么**：
- ESP-IDF 组件化的核心机制：`REQUIRES`（公开依赖，传递给引用者）vs `PRIV_REQUIRES`（私有依赖，仅自己用）——正确区分能显著减少头文件路径污染
- 报错信息直接告诉你怎么修，**读懂构建系统的报错比瞎猜高效一百倍**
- `esp_timer`（微秒级定时器）这类基础组件在旧 IDF 是"免费"的，新 IDF 要显式声明——升级 IDF 大版本时这类报错会集中出现

## #006 IDF 5.x → 6.x 的 esp_lcd API 改名，厂商驱动编译失败

**日期**: 2026-09-25
**阶段**: 阶段 1 编译

**现象**：
厂商 LCD 驱动编译报三种错：
```
error: unknown type name 'lcd_color_rgb_endian_t'; did you mean 'lcd_color_range_t'?
error: 'LCD_RGB_ENDIAN_BGR' undeclared; did you mean 'LCD_RGB_DATA_ENDIAN_BIG'?
error: implicit declaration of function 'esp_get_chip_model'
```

**原因**：
厂商例程基于 IDF 5.x 编写，IDF 6.x 完成了一轮 API 清理：
- `lcd_color_rgb_endian_t` → `lcd_rgb_element_order_t`（语义也更准确：是"RGB 元素顺序"不是"字节序"）
- `LCD_RGB_ENDIAN_BGR` → `LCD_RGB_ELEMENT_ORDER_BGR`，结构体字段 `rgb_endian` → `rgb_ele_order`
- `esp_get_chip_model()` 没有了，用 `esp_chip_info()` 取而代之

**解决**：
给厂商驱动的副本打补丁（共 4 处）：
1. `Vernon_ST7789T.h`：结构体里废弃的 union 换成 `lcd_rgb_element_order_t rgb_ele_order`
2. `Vernon_ST7789T.c`：switch 的枚举值换成新名
3. `ST7789.c`：`.rgb_ele_order = LCD_RGB_ELEMENT_ORDER_BGR`
4. `main.c`：改用 `esp_chip_info()`

**学到什么**：
- **编译器报错里的 "did you mean" 建议不能盲信**——它建议的 `lcd_color_range_t` 是错的，正确答案要去官方头文件（`esp_lcd_types.h`）里找
- 为什么保留厂商的 Vernon_ST7789T 副本而不换官方驱动：这块屏是 ST7789"T"变体，需要自定义伽马(0xE0)+反色(0x21)初始化序列，官方驱动序列不匹配
- 移植旧代码到新 IDF 的套路：类型改名 → 头文件里 grep 新名字 → 逐个替换，90% 的编译错误都能这样解决

## #007 IDF 6.x 移除了内置 json 组件；HTTP 状态码枚举改名

**日期**: 2026-09-25
**阶段**: 阶段 2 编译

**现象**：
1. CMake 配置阶段直接失败：
   ```
   Failed to resolve component 'json' required by component 'main': unknown name.
   ```
2. 修完后又报 `'HTTPD_413_PAYLOAD_TOO_LARGE' undeclared; did you mean 'HTTPD_413_CONTENT_TOO_LARGE'?`

**原因**：
1. IDF 6.x 删掉了内置的 `json`(cJSON) 组件，改为**组件管理器**（Component Manager）从乐鑫官方 registry 按 `idf_component.yml` 声明拉取——这是 IDF 5.1 以来的方向：官方做减法，第三方库走包管理。
2. `HTTPD_413_PAYLOAD_TOO_LARGE` 跟随 HTTP 语义修订改名 `HTTPD_413_CONTENT_TOO_LARGE`（"Payload" → "Content"，对齐 RFC 9110）。

**解决**：
1. `main/idf_component.yml` 里声明 `espressif/cjson: "^1.7.19"`，CMake 的 REQUIRES 写 `espressif__cjson`（registry 组件命名规则：`命名空间__组件名`）
2. 换用新枚举名

**学到什么**：
- 组件管理器是 ESP-IDF 版的"pip/npm"：依赖写在 `idf_component.yml`，首次构建自动下载缓存到 `~/.espressif/component_cache`，之后离线也能编
- 判断某内置组件是否被移除：去官方 examples 里搜同类用法，看它现在怎么声明依赖（我就是在 `examples/protocols/http_server/restful_server` 里找到答案的）

## #008 hook 发送偶发"操作超时"——WiFi 省电模式的延迟陷阱

**日期**: 2026-09-25
**阶段**: 阶段 3 hook 联调

**现象**：
curl 直连 ESP32 一直正常；但 PowerShell hook（`Invoke-WebRequest -TimeoutSec 2`）偶发"操作超时"。板子明明在线，稍后再发又能通。

**原因**：
ESP32 WiFi 默认开启**省电模式**（`MIN_MODEM`）：空闲时射频休眠、按路由器的 DTIM 周期定期醒来收信标。设备休眠后第一个进来的包，要等射频唤醒+关联状态恢复，延迟可达几百毫秒到数秒。之前测试"curl 能通"其实是连续测试把无线活动维持住了，掩盖了问题——**测试节奏本身会改变被测系统的状态**。

**解决**：
固件里 `esp_wifi_set_ps(WIFI_PS_NONE)` 关闭省电 + hook 超时放宽到 3 秒。桌面常供电设备用功耗换响应速度是正确取舍。

> ⚠️ **本条结论已被 #010 推翻**：后续 A/B 实验证明本环境下 `WIFI_PS_NONE` 反而导致
> TCP 握手间歇卡 3 秒，固件最终回到默认的 `WIFI_PS_MIN_MODEM`。保留本条作为
> "第一版归因"记录，以 #010 为准。

**学到什么**：
- `esp_wifi_set_ps()` 的三档：`WIFI_PS_MIN_MODEM`（默认，按 DTIM 睡）/ `WIFI_PS_MAX_MODEM`（睡更狠）/ `WIFI_PS_NONE`（不睡，延迟最低）
- 排查"偶发超时"要先问：设备两次请求之间处于什么状态？省电、缓存、连接池都可能让"第 N 次"和"第 1 次"行为不同
- hook 类工具的超时要覆盖"最坏情况唤醒时间"，2 秒对休眠设备太紧

## #009 权限确认后红灯卡死——事件注册不全

**日期**: 2026-09-25
**阶段**: 阶段 3 真实使用反馈

**现象**（用户报告）：
黄灯亮着（AI 工作中），Claude 请求权限 → 红灯。在电脑上点了"允许"后，灯**一直红**不变黄，直到本轮结束才变绿。

**原因**：
事件流断档。最初只注册了 5 个事件（SessionStart/UserPromptSubmit/Notification/Stop/SessionEnd）。
权限批准后 Claude 继续干活，但到本轮 Stop 之间**没有任何已注册事件触发**——灯停留在最后一次事件（红）的状态。

**解决**：
补注册 `PreToolUse` / `PostToolUse`（每次工具调用前后触发，映射为 WORKING 黄灯）。
权限一批准、被批准的工具开跑，PreToolUse 立即把灯拉回黄。

**学到什么**：
- 调试状态机问题的第一步：**把完整事件时间线画出来**，对着线找"哪段没有事件覆盖"
- hook 系统的语义：UserPromptSubmit 只在"用户提交输入"时触发，权限批准不是用户输入，不触发它
- 灯显示的是"最后一个事件的状态"，没有事件就没有状态变化——这是事件驱动架构的固有特性，设计时要保证每个交互阶段都有事件

## #010 状态更新慢的三层排查：PowerShell 启动 → WiFi 省电 → 2.4G 射频

**日期**: 2026-09-25
**阶段**: 阶段 3 真实使用反馈

**现象**（用户报告）：状态更新不及时。实测 hook 一次要 3.3 秒。

**排查过程（三层递进，每层都真实存在）**：

1. **PowerShell 冷启动 3.3s**——实测 5 次全部 3.2~3.4s。每次 hook 都要拉起新的 powershell.exe（.NET 运行时初始化+杀毒扫描）。
   → **解决：hook 直接调系统自带 `curl.exe`**（冷启动约 50ms）。
   巧妙设计：`curl --data-binary @-` 把 Claude Code 喂进 stdin 的原始 JSON 直接 POST 给板子，
   事件类型放 URL query（`/events?event_type=pre-tool-use`），**电脑侧零脚本**；固件增加 query 解析。

2. **换 curl 后仍偶发 3s 卡死**。用 `curl -w '%{time_connect}...'` 分段计时定位：**TCP 握手本身卡 3 秒**（SYN 重传），握手成功后 HTTP 只要 30ms。排除应用层。
   先怀疑 `WIFI_PS_NONE`（为修 #008 加的），A/B 实验撤掉——**依然卡**，不是它。

3. **定位到 2.4G 射频质量**：ping 延迟 12~347ms 剧烈抖动；暖链路连发也随机卡（排除省电唤醒）；
   路由器与板子协商在 40MHz 频宽（HT40）——2.4G 的 HT40 在干扰环境下出了名的丢包重传。
   → **缓解：固件强制 HT20**（`esp_wifi_set_bandwidth WIFI_BW_HT20`）+ hook 加 `--retry 2`（状态设置幂等，重复无害）。
   最终实测：0.5~1.0s，6/6 成功。

**学到什么**：
- 性能问题要**分段测量**而不是猜：`curl -w` 的 time_connect/time_starttransfer 一行命令就能把"网络问题"切成"TCP 握手问题"和"服务器响应问题"
- Windows 上"每个事件起一个进程"的 hook 设计，进程启动成本是第一嫌疑（PS 3.3s vs curl 50ms，差 60 倍）
- A/B 实验一次只改一个变量：撤 PS_NONE 单独验证，才没有把两个问题混在一起
- 2.4G 没有银弹：HT20 换稳定、重试换兜底，剩下的靠路由器侧优化（见遗留问题）

**遗留**：
- 路由器侧可再优化：给板子 MAC 绑定静态 IP（防 DHCP 变化）、2.4G 信道选 1/6/11 中最空的
- 偶发 >1s 延迟在恶劣射频环境下仍可能出现的，hook 的重试保证"最终送达"

## #011 "Stop hook error: Failed with non-blocking status code"——hook 失败不该惊扰用户

**日期**: 2026-09-25
**阶段**: 阶段 3 真实使用反馈

**现象**：
Claude Code 界面弹出：
```
Stop hook error: Failed with non-blocking status code: No stderr output
```
且板子停在红（ERROR），stop 事件确实丢了。

**原因**（两层）：
1. 事件丢失：那一瞬间 2.4G 射频坏窗口，curl 3 次尝试全超时（exit 28）。
2. 警告弹出：Claude Code hook 约定——exit 0 正常 / exit 2 阻断 / **其它非零码 = 非阻断警告**。
   curl 失败的非零退出码被当成了"hook 出错"展示给用户，但 `curl -s` 静默模式又没有 stderr 输出，于是显示成"No stderr output"。**AI 工作本身不受影响**。

**解决**：
hook 改为 `cmd /c ai_status_hook.cmd <event>` 包装：
- 批处理里最后 `@exit /b 0`——**无论 curl 成败都返回 0**，hook 永不向 Claude Code 报错
- `%SystemRoot%\System32\curl.exe` 全路径调用，规避不同 shell 环境 PATH 解析到不同 curl 的歧义
- `>nul 2>&1` 由 cmd 自己重定向到空设备，规避 `-o NUL` 在 MSYS/cmd 两种环境下语义不同的坑
- 重试升到 3 次；包装脚本由安装器从 BOARD_URL 模板自动生成（IP 只维护一处）

**学到什么**：
- hook 生态的退出码语义就是 API 契约：写集成前先查清楚 0/2/其它 分别代表什么
- "警告用户"本身也是成本：无法行动的警告（网络抖动）应该被系统吸收掉而不是抛给人
- 每层加一个"兜底壳"是集成的常见手法：功能层（curl）保持纯粹，壳层（cmd）负责容错语义
- cmd 批处理启动 ~20ms，是 Windows 上比 PowerShell 轻 100 倍的胶水层（但切记 ASCII only，见 #004）

## #012 Claude Code 启动报"not a valid application"——npm 拦截 postinstall 留下假二进制

**日期**: 2026-09-25
**阶段**: 阶段 3/5 验收期间（环境事故，非本项目代码问题）

**现象**：
```
程序'claude.exe'运行失败: The specified executable is not a valid application for this OS platform.
```

**原因**：
`claude.exe` 只剩 500 字节——是个打印错误提示的**文本占位符**。Claude Code 的真实二进制要靠
npm 包的 postinstall（install.cjs）或平台可选依赖下载；这台机器的 npm 启用了 allow-scripts
安全机制，**postinstall 被拦截**，自动更新后就留下了占位符。

**修复**：
```powershell
npm install -g @anthropic-ai/claude-code@latest --registry=https://registry.npmmirror.com
```
镜像源重装后二进制直接就位（242MB 真身），`claude --version` 验证通过。
若将来再坏（自动更新+脚本被拦），同款命令即可修复；或手动 `node node_modules/@anthropic-ai/claude-code/install.cjs`。

**学到什么**：

## #013 会话结束后灯卡黄，之后莫名变红——丢失终态事件 + 单灯下的语义噪音

**日期**: 2026-09-25
**阶段**: 阶段 3/5 真实使用反馈

**现象**（用户报告）：
两个 AI 会话都结束很久，灯一直黄 → 后来变红 → 直到退出 Claude 才熄灭。

**解剖（三个现象三个原因）**：
1. **卡黄**：Stop（完成）事件在糟糕的射频窗口里连 3 次重试全丢。灯停留在最后一个成功事件（working），无自愈机制 → 永久卡黄
2. **变红**：Claude Code 的闲置提醒（60 秒没互动 → Notification）。ai-light 桌面版语义里"该你介入了"= 红，属于逐级升级设计；但单灯无上下文场景下，用户读到的是"出错了？"——语义噪音
3. **退出熄灭**：SessionEnd 事件送达 → idle ✓（这部分完全正常）

**修复（两个互补的自愈机制）**：
1. **Notification 细分**：报文里带 message 文本——含 "permission" → 红（真需要人）；闲置提醒 → 绿。
   副作用成为特性：闲置提醒变成丢失 Stop 的自愈信号（最迟 60 秒，卡黄自动修复为绿）
2. **看门狗**：显示任务在黄灯状态下带 3 分钟超时等队列，超时自动转绿。
   依据：真实 AI 工作时每次工具调用都有事件（几秒一个），3 分钟静默 ≈ 终态丢失。
   代价：连续 3 分钟纯思考不调工具会被误判为完成（可接受）

**学到什么**：
- **事件驱动系统必须为"事件丢失"设计兜底**：要么周期心跳，要么超时推断，否则状态机会卡死在最后收到的事件上
- **同一事件的语义要按上下文区分**：桌面版逐项目显示时"闲置=红"是合理升级；单灯无上下文时它是噪音——移植语义要想清楚信息量变了
- cJSON 指针陷阱：`cJSON_GetStringValue` 返回的是树内指针，**树释放后指针悬空**；需要跨块使用时，树必须活到用完再统一释放（本次修改就差点引入 double-free）
- FreeRTOS 技巧：`xQueueReceive` 的超时参数天然可以当看门狗用——portMAX_DELAY 是死等，带超时则"等事件或超时二选一"

## #014 ZCode 会话对灯"完全无响应"——配置只在进程启动时读取 + 一次归因错误

**日期**: 2026-09-25
**阶段**: 阶段 5 真实使用反馈

**现象**（用户报告）：
灯对 ZCode 会话完全无响应（我正在跑命令，灯却一直 IDLE）。

**排查过程**：
1. 板子在线（curl /state 有响应）→ 排除板子和网络
2. ZCode 日志：全天所有启动记录 `hookCount=0`，且无任何 hook 执行记录
3. 配置文件校验：JSON 有效、hooks.enabled=true、7 事件齐全 → 配置本身没问题
4. **决定性证据**：`Get-Process` 显示 ZCode 所有进程启动于 22:02~22:26，
   而 hooks 安装于 23:34——**宿主进程比配置早，且从未重启**。
   配置文件 hooks 只在进程启动时加载。

**解决**：完全退出并重启 ZCode（会话可恢复）。

**附带澄清一次归因错误**：
之前"黄灯就是我"的判断是错的——当时宿主进程没加载 hooks，我的会话从未触发过事件；
那个黄灯是手动测试的残留状态，恰好与"我在干活"重叠。
看见"灯黄 + 我在干活"就归因为因果，是典型的**相关≠因果**错误。
正确的验证方法当时就应该做：**停手 10 秒看灯是否变化**（受控实验），而不是拿巧合当证据。

**学到什么**：
- **配置类问题先问加载时机**：配置是启动读一次还是热加载？答案决定了"改了配置为什么不生效"
- 排查链条的顺序：板子→网络→配置内容→**配置加载时机**→进程启动时间，一层层收紧
- 归因要靠受控实验：A 发生时 B 在发生 ≠ A 导致 B；停掉 A 看 B 是否还在，才是证据
- `Get-Process` 的 StartTime 是 Windows 上查"进程比配置新还是旧"的最快手段

## #015 ZCode hooks 六轮攻坚全记录——教科书级的分层排查

**日期**: 2026-09-25 ~ 09-26 深夜
**阶段**: 阶段 5（ZCode 支持）

**最终成功配置**（三层组合，缺一不可）：
- 插件 `ai-status-hooks@0.1.2`：**command 型** hook（`cmd /c "脚本" 事件`，timeout 秒）
- 包装脚本 v3：自记日志首行 + 硬编码 curl 路径 + 双档重试 + 永远 exit 0
- 固件：**不拒绝大 body**（流式读，只解析首块 JSON）

**六轮排查链**（每轮一个假设、一次验证）：

| 轮 | 假设 | 验证结果 | 关键证据 |
|---|---|---|---|
| 1 | 进程比配置旧，没读到 hooks | ✅ 部分对 | Get-Process StartTime=22:02 < 安装 23:34，重启后仍不触发 |
| 2 | statusMessage 字段违规被丢 | ❌ | 去掉后依旧（官方文档两处自相矛盾，按严格版执行是对的，但不是主因） |
| 3 | 插件机制激活 runner | 🔸 半对 | hookCount=7 证明注册成功，且 config hooks 开始执行（留失败记录）——但插件自身 hooks 不执行 |
| 4 | 新会话快照旧 | ❌ | 新任务 + 重启都不行 |
| 5 | process 型孵化失败（裸名 cmd） | 🔸 接近 | Python 模拟"全路径+参数数组+stdin"孵化成功且灯亮！但 ZCode 里全路径依然 9ms 失败 |
| 6 | 换 command 型 + 固件 413 拒大 body | ✅✅ | 自记日志证明孵化成功；修掉 413 后灯随工具调用实时变化 |

**最终定位的两个真凶**：
1. **ZCode 的 process 型孵化在我们环境就是起不来**（9ms 即败，原因未明）——换 command 型走 shell 链解决
2. **固件 512 字节 body 上限把真实事件全拒了**：ZCode/Claude 的真实 payload（带 transcript 路径、完整工具参数）轻松超限被 413，而 curl 无 -f 标志对 413 也退出 0——wrapper"成功"，灯却没反应

**学到什么**：
- **测试要用真实数据**：手动测试的小 JSON 全部通过，真实事件全军覆没——凡是"手动测试好好的、真实流量不行"，第一反应查数据形状差异（大小、字段、编码）
- **给脚本装黑匣子**：wrapper 第一行写自记日志，一次实验就切开了"没孵化"vs"孵化后失败"两种假设——比反复猜快十倍
- 文档自相矛盾时按严格版执行（坑清单 > 正文描述），但要有"这可能是文档错误"的备选假设
- process 型孵化在宿主环境可能失败时，command 型（shell 链）是可靠的退路；`cmd /c "..."` 写法在 cmd/PowerShell/bash 下语义一致
- HTTP 客户端没有 -f 时，4xx/5xx 也是"退出 0"——**协议层成功 ≠ 业务层成功**

## #017 局部刷新的双层坑：区域指针 + 行距连续性

**日期**: 2026-09-26
**阶段**: 阶段 4 灯效状态机 v2

**现象**（用户两次肉眼报告）：
1. "灯没有反应"——/state 一切正常，屏幕灯不亮
2. "在闪，但不是圆，是框出的正方形在闪"——修复一层后，圆被撕成方块碎片

**原因（两层，都是 esp_lcd_panel_draw_bitmap 的契约）**：
该 API 把数据指针当作"区域自己的像素流"按 width×height 顺序读取：
1. 传帧缓冲开头 s_frame → 左上角背景像素被灌进灯区域 → 灯永远暗

**解决**：局部区域先按行距拷贝进独立的连续缓冲（s_lamp_buf 77×77），再传给驱动。

**学到什么**：
- 图形 API 的"指针契约"要读三遍：指向谁、怎么排列、生命周期（DMA 异步读需要缓冲存活）
- 全屏刷新能跑 ≠ 局部刷新能跑：从全量切到增量是契约敏感操作
- 肉眼是最终验收：/state 验证的是逻辑状态，像素对不对只有屏幕说了算——

1. ZCode payload 用驼峰(sessionId/hookEventName)，固件只认下划线——全部落进 "?" 公共桶
2. Claude 的 pre/post-tool-use 带完整工具参数(常超512字节)，流式读取只留首块(#015 遗留)，
   **截断的 JSON 让 cJSON_Parse 整体失败**——大事件也落 "?"，把 "?" 的 tool 撺成 claude，
   下一条 zcode 事件又抢回来 = "logo 闪变"；批准后恢复事件(大payload)同样丢失 = 卡 APPROVE

**解决**：
- 字段兼容双命名(session_id/sessionId 等)
- 关键字段改 **字符串扫描提取**(json_scan_string)：所需字段都在 payload 开头，
  对截断免疫；cJSON 整体解析从事件路径退役

**学到什么**：
- "部分解析"策略的正确实现不是"解析前512字节的JSON"(截断=非法)，而是**按需扫描字段**
- 排查"数据明明在却不生效"：加探针把原始输入打出来(无主事件探针一击定位)
- 修复顺序很重要：先让字段解析对截断免疫，双命名兼容才有意义

## #026 槽位复用继承旧字段——zcode 卡显示别人的 token

**日期**: 2026-09-26
**阶段**: 阶段 4 token 显示联调

## #027 进程被杀后卡片残留——事件驱动系统的"静默死亡"与进程看门狗

**日期**: 2026-09-26
**阶段**: 阶段 4 真实使用

**现象**（用户报告）：
杀掉 Claude 进程后，屏幕上的卡片还在红闪（持续 400+ 秒），直到板子重启。

**根因**：
hook 是事件驱动的——**进程被 kill 不产生任何事件**（OS 行为，AI 工具自己也不知道）。
板子停留在最后收到的状态上无限延续。这是所有事件驱动系统的固有盲区。

**解决**（移植 ai-light 参考项目的"进程扫描兜底"设计）：
1. 固件加 `POST /sessions/clear?tool=&id=` 清理端点（id 前缀/tool/全清 三档）
2. 主机侧看门狗 `hook/esp_light_watchdog.py`（pythonw 常驻，3 秒巡检）：
   - claude（CLI 1 进程=1 会话）：存活数 == 0 且板上有卡 -> 全清；
     存活数 < 卡数 -> 清空闲最久的
   - zcode（Electron 多进程）：应用不在 -> 全清
   - **防护**：只清 idle>=10s 的卡（进程检测万一失效也不误杀活跃会话）；

3. 开机自启：Startup 快捷方式（PID 存活 + 端到端测试均通过）

**实测**：真实死卡 429 秒未被清理 -> 看门狗启动后 1 秒清除；
模拟残留卡 14 秒内自动清（含 10s 防护）。

**学到什么**：
- 事件驱动系统的完整性要求**每个"活跃"概念都有对应的"死亡"检测**——
  否则"最后状态"会变成"永久状态"（和 #013 的终态丢失是同一哲学）
- 兜底检测的设计原则：**宁可少清不可误清**（grace 期 + 异常即跳过 + 存活数匹配）
- 看门狗这类"主动巡检"与 hook"被动通知"互补，是物联网设备的标准双通道

## #028 ZCode 批准后卡片迟迟不回 WORKING——hook 看不见"批准"，但日志看得见

## #030 hook 阻塞 AI：把网络移出关键路径（本地队列 + 常驻转发）

**日期**: 2026-09-26
**阶段**: 性能架构优化

**背景**：
两个工具都**同步内联**执行 hook（ZCode 官方：async 无运行时效果，hooks 永远内联）。
实测每次事件 AI 要等 310-643ms（好网络），抖动时 2.3-4.5s，最坏一次 15s（重试耗尽）。
本机 2.4G 环境往返 0.3-2.7s——网络在 AI 的关键路径上，这是不可接受的架构缺陷。

**方案：本地文件队列 + 常驻看门狗转发**
```
hook (wrapper v5) → 写本地 .ev 文件 (~33ms, 零网络)
                       ↓
看门狗(常驻, 每1s) → 按 mtime FIFO 转发 → 成功即删
                     失败首条即停(保序) → 下轮重试 → 180s 过期丢弃
```

**关键设计**：
- 队列条目 = **文件名编码元数据 + 文件内容为原始 body**：
  `<event>_<src>_<rand>[_t<tok>].ev` ——批处理零解析、零转义风险，
  token 这类附加参数直接放文件名（`_t107881`）
- **首败即停**（而不是跳过继续）：保证 FIFO 不破坏（状态机需要顺序），
  且一轮不会被几十条重试拖死
- 4xx = 毒条目立即删；5xx/超时 = 保序重试
- 网络 POST 超时收紧到 2s（本机实测往返 0.3-2.7s 的平衡点）

**实测**：hook 阻塞 300-1000ms → **33ms**；端到端（灯变化）~2.2s
（队列周期 1s + 网络 0.3-2s）；WiFi 全断时 AI 零感知。

**学到什么**：
- **外部 IO 不进关键路径**是通用架构原则：hook/FUSE/中断处理都是同一个套路——
  写本地持久队列，由常驻进程做可靠投递
- 队列实现的关键选择：**文件名编码元数据** 让"最笨的写入方"（批处理）也能安全入队
- 失败处理要区分"保序"与"推进"：状态机类消费者必须保序，宁可停一轮

## #054 DONE 后卡片消失但电脑上任务还在——两个"误杀阈值" + 事件丢失无恢复

**日期**: 2026-09-26
**阶段**: 用户验收

**现象（用户报告）**："Claude 是心跳没了吗，done 之后现在页面清除了，但是电脑还有这个任务"。

**根因（三层叠加）**：
1. **GHOST_TIMEOUT 10 分钟太短**：非工作态（DONE）无事件 10 分钟就清卡——但"回合完成后
   等用户输入"的会话本身就是空闲的，会一直被误清
2. **WORKING_KILL 5 分钟太短**：长思考/长生成期间无工具事件 → 超时被判"疑似被杀"清卡
   （与 #052 的 STUCK 误判同源：**用工具事件的心跳去衡量没有工具事件的思考过程**）
3. **事件丢失无恢复**：会话的 session-start 因网络坏窗口在队列里老化丢弃 → 板子上
   根本没建立卡，之后会话空闲不产生新事件 → 卡永远不出现

**解决**：
- `WORKING_KILL_MS` 5min → **30min**；`GHOST_TIMEOUT_MS` 10min → **60min**

- 看门狗新增**两级重建**：
  a. token 推送返回 `updated:0`（板上无此卡）→ 补发 `session-start` 重建（限流 60s）
  b. 进程巡检发现 **claude 进程在跑但板上无 claude 卡** → 用**最近活跃的转录文件**重建
     （转录文件名即权威会话 id）——覆盖"空闲会话转录不增长"的场景

**实测**：日志出现 `claude 进程 1 个但无卡 -> 重建最近会话 cea5c78d`，板子上卡恢复 ✓

**学到什么**：
- **"清理机制"的阈值必须按"最慢的正常行为"设计**（长思考、长时间空闲）；清理的
  理由是"能证明它死了"（看门狗有进程视野），而不是"它安静了太久"
- 有"删除"路径就应有"重建"路径：事件驱动系统的自愈 = **发现缺失 → 用权威源补发**
  （转录文件是比事件流更权威的存在证明）

**日期**: 2026-09-27
**阶段**: 用户验收（压测 #055 恢复之后）

**学到什么**：
- #060 结论"转录无法区分死活"落地后，重建窗口必须**紧**——
  窗口越宽，把死会话当活的概率越大
- 修复参数时问一句："这个值服务什么场景？" 场景是"刚被误清的会话"，
  那窗口就该是分钟级，不是小时级

## #065 复查 #056~#063：两处"已修复"实际没生效——兜底 except 与样本巧合

**日期**: 2026-09-27
**阶段**: 代码复查（用户："又修复了一些问题，检查一下"）

**背景**：
#056~#063 的修复全部落在电脑侧（`hook/` + `tools/`，固件未动）。复查这 9 个提交，
发现 **2 处"已修复"实际未生效**，另有 4 处稳健性/一致性问题。

**现象 1：#062 的状态推断从未生效**
`hook/esp_light_watchdog.py:365-368`：

```python
tail_lines = fh.read().decode("utf-8", "replace").split("\n")   # list[str]
for raw in reversed(tail_lines):
    raw = raw.strip()                                            # str
    if not raw.startswith(b"{"):                                 # ← TypeError
```

`str.startswith(bytes)` 抛 `TypeError`，被 `:380` 的 `except Exception: pass` 吞掉，
`infer` 恒为 `"stop"` —— 即 #060/#062 要修掉的"无脑置 DONE"。而日志照常打印
`重建 xxx 恢复状态=stop (#062)`，看不出任何异常。实测：

```
EXC: TypeError startswith first arg must be str or a tuple of str, not bytes
```

**根因**：
同文件 `:155-158` 有**正确写法**（`data.split(b"\n")`，全程 bytes）。写 #062 时把
数据源换成了 decode 后的 `str`，却留下了 `b"{"` 字面量 —— **抄了惯用法，没抄数据源**。
真正让 bug 隐身的是那个兜底 `except`：它本意是挡"JSON 解析失败"，实际把编程错误
（TypeError）也一起挡了。

**现象 2：`tools/dump_header.py` 工具必挂**
`hdr_bg` 在 `main():35` 赋值，是**局部变量**；`row():24,26` 引用它 → `NameError`，
同样被 `:28` 的 `except Exception: pass` 吞掉，重试 6 次后抛 `RuntimeError` 让工具死掉。
注释写的是"坏块按背景处理, 避免 '?' 假象"，**与行为正好相反** —— 而这个工具的存在
意义就是排查 #056 的 logo 显示问题，遇到坏块它不会容错，只会死。

**现象 3：#063 的"强制恢复"是有条件的**
`tools/stress_matrix.py:359-360`：

```python
api("/events?event_type=pre-tool-use&ts=1", {"session_id": "ts-final"})
ev("session-end", "ts-final")        # ← 会追加全局 TS
```

`:64` 的规则是"URL 已含 `ts=` 就不再追加全局 TS"，所以第一行安全。但第二行 `ev()`
的 URL 不含 `ts=` —— **若此刻全局 `TS` 仍是 `"&ts=30"`，就会把 ts=1 覆盖回去**。
当前跑完不会触发（`test_timeouts():266` 已清空全局 TS），故属**潜在**问题；但注释
声称"强制"，实际依赖一个没写出来的前提。D 段一旦提前失败而 main 继续，兜底就失效
——恰是 #063 要防的场景。

**为什么"实测 ✓"没抓住**：
- #062 文档记"实测：cea5c78d 尾部是 text → 推断 DONE，与实况一致 ✓"。但 **text 走
  降级路径得到的也是 DONE** —— 样本恰好与故障产物一致，通过纯属巧合。换一个尾部是
  `tool_use` 的转录来测，立刻露馅。
- #063 文档记"板子已**手动**恢复" —— 脚本层修复从未端到端跑过。#064 里"以后跑压测
  不会再发生"这个结论，也因此缺少支撑。

**解决（已于 2026-09-27 落地，5/5 项全部验证）**：
1. `esp_light_watchdog.py:368` → `raw.startswith("{")`（或该段统一用 bytes）
2. `dump_header.py` → `hdr_bg` 提为模块级常量
3. `stress_matrix.py:359-360` → 合成一次调用，显式且不被追加：
   `api("/events?event_type=session-end&ts=1", {"session_id": "ts-final"})`
4. `demo_video.py:132-146` → 残留断言区分"验证通过"与"未能验证"：4 次 `/state` 全失败时
   `leftover` 保持 `[]`，会打印"干净 ✓"——**从未验证却报成功**，与 #058 同类
5. `esp_light_watchdog.py:347` 删过期注释（"2小时内"已被 #061 的 15min 取代）；
   `:353` 给 `os.path.getmtime` 加保护（glob 与 getmtime 之间文件可能被删 → OSError
   会让整轮 `proc_rules` 跳过，看门狗不死但那一轮的清卡也一起跳过）

**学到什么**：
- **"吞掉一切"的兜底要反问一句**：如果我这段代码本身写错了，异常会不会也被吞掉、
  变成静默降级？只该捕获预期内的异常（这里是 `json.JSONDecodeError`），
  编程错误必须炸出来
- **验证的样本必须能真正走到被验证的分支**。拿一个"A 分支和 B 分支结果相同"的样本
  去测 A 分支，测了等于没测 —— 还留下"已验证"的假安全感
- **手动善后 = 修复未经验证**。现场是人手收拾的，脚本的兜底就没被检验过。
  下次复现时让脚本自己收尾，别插手
- 复查也要看**注释与代码是否还一致**：本批 2 处注释描述的行为与代码实际行为相反
  （`hdr_bg` 的"容错"、`:347` 的"2小时内"），注释密度越高，过期注释的干扰越大
